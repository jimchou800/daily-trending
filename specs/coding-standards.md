# AI 开源项目热点日报 · 编码规范 v1.0

状态：已完成逐条评审，作为项目开发与维护约束。
更新日期：2026-11-10。

本规范约束开发与质量验证，不决定产品功能或技术栈。产品范围以 [项目规格](project-vision.md) 为准；根目录 [AGENTS.md](../AGENTS.md) 第 10 节同步纳入下列条款。修改编码要求时同步维护两份文件，不得据此降低产品 spec 的验收标准。

## 编码与质量规则

### CS-01 · 适用范围

本规范不决定技术栈。项目采用 Python 时适用 Python 规则，采用 TypeScript 时适用 TypeScript 规则；不得为满足规范引入原本不需要的语言或工具链。具体工具、命令及配置路径随技术选型确定，不编造尚不存在的检查命令。

### CS-02 · Python 格式

若采用 Python，使用 Black 格式化自维护的 Python 源码、测试及脚本，排除第三方代码、自动生成文件和构建产物。Black 版本与配置纳入仓库管理，本地和 CI 使用同一套。CI 使用检查模式，格式不符即失败并阻止合并，不在 CI 中自动改写文件。

### CS-03 · TypeScript 类型检查

若采用 TypeScript，自维护的 TS/TSX 源码、测试及脚本均纳入 strict 类型检查，CI 类型检查失败则阻止合并。禁止无理由的显式 any、@ts-ignore 和文件级 @ts-nocheck。外部不可信数据先用 unknown 接收并校验，不以类型断言替代数据校验。确需兼容第三方类型缺陷时，仅允许附具体原因的局部例外，优先使用可检测失效的 @ts-expect-error。

### CS-04 · 公开函数文档

公开函数指供模块外调用的函数、公开方法及框架要求的入口函数，不以是否向网站用户提供 API 为判断依据。Python 内部辅助函数使用下划线前缀；TypeScript 非导出辅助函数不强制写文档。

公开函数必须有 docstring 或 JSDoc，说明用途、调用约束，以及不明显的返回值、副作用和异常。不要求重复类型声明或机械罗列参数；文档应描述实际调用契约，不能只以非空注释充数。

### CS-05 · 业务字符串约定

状态值、协议标识、配置键等业务约定统一定义，使用常量、枚举、字面量联合类型或集中 schema，避免多处手写造成不一致。普通展示文案、局部可理解的一次性字面量和测试样例可直接书写，不机械提取常量。外部输入仍须校验，常量定义不能替代校验。

### CS-06 · 待完成工作

自维护代码、测试及配置合入 main 时，不保留表示待完成工作的 TODO、FIXME 等占位标记；第三方及自动生成文件不在扫描范围。非当前范围的后续工作记录到 issue 或规划文档。

当前产品 spec 要求的能力必须完成，不能通过删除注释、换标签、关联 issue 或跳过测试掩盖缺失。CI 扫描明确标记，评审检查实际完整性；扫描语义及例外按 CS-14 执行。

### CS-07 · 覆盖率与关键场景

单测行覆盖率和分支覆盖率均不得低于 80%，分别设为 CI 门槛。产品 spec 明确列出的关键边界必须有对应测试，总体覆盖率达标不能替代逐项验证，自动测试也不能替代发起人的产品验收确认。

### CS-08 · 覆盖率统计边界

覆盖率以本仓库自维护的生产代码为分母，包含实现业务逻辑的脚本；排除测试代码、第三方依赖、自动生成代码、构建产物及纯声明/类型文件。排除项在仓库覆盖率配置中显式列出，CI 生成可审计报告，不只查看本地摘要。

### CS-09 · 未执行文件与多语言统计

显式配置生产代码统计范围，未被测试加载或执行的生产文件同样纳入，覆盖率按零计，不得仅统计已加载文件。若同时采用 Python 和 TypeScript，两套代码分别满足行覆盖率及分支覆盖率 ≥80%，不得合并数字互相抵消。

### CS-10 · 单测与集成验证

单元测试不依赖真实网络、付费模型或线上发布，使用可控替身验证逻辑。同时必须提供集成测试，使用保存的榜单与模型响应样本，贯通真实解析、校验、筛选、页面生成及发布产物检查。

只 mock 外部边界，不将待验证的内部逻辑替换掉。覆盖率达标不能替代集成验证；CI 不要求每次调用付费服务，固定样本集成测试也不能替代上线环境验证和发起人验收确认。

### CS-11 · CI 与 main 合并门槛

按实际技术栈，将格式检查、lint、类型检查、单测、覆盖率及集成测试设为必需检查。任一必需检查失败、取消或未执行，均不得视为通过；不得通过 continue-on-error、忽略退出码等方式绕过。不适用的检查明确标注，不创建空任务冒充通过。

main 禁止直接推送，配置分支保护要求相关必需检查成功后才能合并。分支保护未配置或无法落实时如实报告，不能仅凭本文件声称门槛已落实。临时隔离测试的适用边界按 CS-13 执行，不能据此绕过必需检查。

### CS-12 · lint 职责与抑制

格式检查、lint、类型检查分别定义职责，不得互相冒充。按选定技术栈配置适用的 lint 工具，至少检查未使用变量或导入，以及工具可检测的常见错误。

规则及工具版本纳入仓库管理，本地与 CI 一致。禁止为使检查通过而全局关闭规则；局部抑制须说明具体原因。具体 lint 工具在技术选型时确定，不提前锁定。

### CS-13 · 测试执行完整性

必需测试不得保留 only 或允许无测试成功的配置。产品 spec 的关键场景不得通过跳过测试或预期失败标记视为完成；发现这些情况，CI 应失败。

其他确需临时隔离的测试必须注明原因、关联跟踪事项，并明确报告未验证范围，不计为已通过；是否允许合并须由维护者明确决定。该例外不适用于 spec 关键场景，也不将失败、取消或未执行的必需检查变为成功。

### CS-14 · 待办扫描语义与例外

区分开发者留下的待完成标记与作为数据的文字。注释、docstring 等位置中的待办占位标记禁止合入；测试样本、普通字符串及规范说明中的同名文字不自动违规，但不得以字符串形式隐藏真实待完成工作。

必要的扫描例外须精确到文件或位置并说明用途，不允许排除整个测试目录规避检查；第三方和自动生成文件仍按 CS-06 排除。

### CS-15 · 测试有效性

测试必须断言可观察的业务结果、边界或副作用，不得仅靠执行代码提高覆盖率。对筛选、去重、预算和发布时间等规则，至少包含能区分正确与典型错误实现的断言。

不复制实现逻辑来计算预期结果，不把“没有抛异常”当作所有场景的充分验证。测试有效性是覆盖率之外的评审要求。

## 验证与落地

实现阶段将条款落实到仓库工具配置、测试及 CI，并提供实际命令与运行结果。检查至少覆盖 Black（若适用）、strict（若适用）、lint、公开函数文档评审、待办标记扫描、两项覆盖率门槛、必需场景测试、集成验证和测试执行完整性。

按 CS-11 验证 main 分支保护实际生效。报告中区分规范已写入、工具已配置、检查已通过、分支保护已生效及发起人产品验收已确认；当前文档定稿不代表这些配置或验收已完成。
