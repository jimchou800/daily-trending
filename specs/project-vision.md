# AI 开源项目热点日报 · 项目规格 v1.1

状态：首版产品范围已确定，可进入实现设计。
更新日期：2026-11-08。

本版纳入 AGENTS.md 评审中确认的 7 项澄清，替换 v1.0 的延迟发布规则。信息来源与内容分析限制约束产品运行流程；开发与维护可查阅必要的技术文档、API 文档和服务定价并验证系统，但不得将这些资料混入日报来源。

## 1. 产品目标

面向有技术背景的普通读者，每天用不超过 10 分钟，了解 GitHub Trending 上值得关注的 AI 项目、热度证据，以及有可靠依据的走红原因。

首要目标是掌握热点。发现新项目、筛选实用工具是辅助价值，不作为排序依据。产品覆盖 GitHub Trending 中的 AI 热点，不承诺覆盖整个 AI 行业或所有热门开源项目。

首版为无需登录的公共静态网站。所有人阅读同一份简体中文日报，可浏览最新一期及历史归档。项目名和必要的英文术语保留原文。每天自动生成并发布，无需人工审核。

## 2. 信息来源与覆盖范围

- 榜单入口固定为 GitHub Trending 的 Daily、全部编程语言榜，不按语言分榜补充候选。
- Daily 使用 GitHub 自身的滚动统计口径，不表述为北京时间前一自然日的完整数据。
- 每次处理该榜单成功返回的全部仓库，保存原始榜单顺序和采集时间；不假设榜单固定有多少条。
- 每期固定使用第一份取得并校验通过的完整榜单快照，作为该期唯一选题依据。后续重试复用快照和已成功的分析，不混用其他快照的候选、顺序或指标；只有尚未取得有效快照时才重新抓取。网页如实展示该快照的采集时间。
- 候选项目必须来自当次榜单。不从 GitHub 搜索、周榜、月榜或其他网站补足数量，接受遗漏榜外热点。
- AI 是项目的核心用途或内容时才纳入，包含模型、应用、工具、基础设施、教程、课程及资源合集。仅提及 AI、实际核心用途与 AI 无关的项目排除。
- Agent 根据仓库描述、README 等 GitHub 信息判断相关性并留下简短依据；证据不足以确认相关性时排除。
- 分析可读取项目在 GitHub 上的 README、仓库元数据、正式 Release 等公开信息。首版不采集站外新闻、社交媒体或链接指向的外部正文。

## 3. 选题与重复收录

每天最多深入介绍 5 个项目。按当次 Trending 原始顺序依次筛选 AI 项目，再应用重复收录规则，取前 5 个符合条件的项目。Agent 不重新评定名次，不按总 Star 数或主观创新性重排。

去重以本期所属日期的北京时间 09:00 为判断基准；历史收录时间也统一按各期所属日期的北京时间 09:00 计算，不取实际采集或发布时间。仅成功发布的日报计入历史，失败尝试、预览、同一期发布重试及内容更正均不新增或重置收录记录。距最近一次收录不足 7 × 24 小时（168 小时）的项目，默认不再介绍；恰好满 168 小时即可正常参与筛选。例如，11 月 1 日收录的项目在 11 月 8 日可重新参与，11 月 2 日收录的仍须去重。

重复窗口内满足以下任一条件才可再次入选：

1. 上次收录后发布了新的正式 Release，不含草稿与预发布版本。
2. 本次榜单展示的当日新增 Star，至少达到上次收录时同口径数值的 2 倍，且确有增长。

热度例外仅在两次数据均存在、上次值大于零时成立；缺失数据或零基数不能用于计算倍数。再次收录必须指出本次变化，并关联上次介绍。比较基准均为最近一次成功收录记录。

不足 5 个时按实际数量发布，不以重复项目或榜外项目补足。只有采集、筛选正常完成并确认没有符合收录条件的项目时，才发布注明“今日无符合收录条件的项目”的一期，说明筛选结果。存在合格候选但全部分析失败属于生成失败，不得发布空日报。

## 4. 每个项目讲什么

正文面向有技术背景的普通读者，不展开代码讲解或深入架构分析。每个项目正文以约 250–400 个汉字为编辑目标，最多 5 个项目；实际阅读时间以试读验收为准。

每条内容包括：

- 项目名、仓库链接、项目类型，以及简短中文介绍。
- 它解决什么问题、适合谁，以及从项目资料中能确认的特点或差异。不声称未经比较验证的领先地位。
- 热度证据：榜单原始位置、采集时间，以及可取得的当日新增 Star、累计 Star。展示指标时标明口径，缺失就标注未获取，不估算、不填零。
- 走红原因：只有存在可引用的证据时才作解释。版本发布等事实本身不等于证明其导致上榜；因果联系无法确认时写“暂未找到明确原因”，可另外陈述已核实的近期动态。
- 资料来源链接，支持读者核对主要事实。再次收录时，补充与上次相比发生了什么变化。

GitHub 资料中的项目宣传不能直接写成已验证事实。无法独立核实的性能、效果等说法应归因于项目方，或省略。不能编造功能、版本、数据、引用或走红原因。

## 5. 网页与发布

- 首页展示最新一期，并显著标明日报日期与实际发布时间；历史归档按日期倒序排列，可打开每一期的独立页面。
- 每期展示采集时间、来源与覆盖范围、项目数量及项目分析。页面适配手机和桌面阅读。
- 每天北京时间 09:00 发布，09:00 是本期发布硬截止点。提前安排采集、分析、校验和必要的重试，不得把旧榜单冒充当天采集结果。
- 只有完整生成且通过校验的一期才自动发布；不公开半成品。正常筛选后少于 5 个项目仍属于完整一期。
- 到 09:00 仍未完成发布就放弃本期，首页显示“今日日报生成失败”，保留上一期及其真实日期。首次运行无日报时保留“尚未发布”，到点后同时说明生成失败。
- 首页根据北京时间、最新一期日期及实际发布时间判断当期缺刊，不得仅依赖生成任务写入失败提示；任务未启动、执行失败或发布失败均须覆盖。历史日报页面不因当期缺刊而被标记为失败。
- 临时故障在预算允许范围内自动重试，每期最多额外重试 2 次，且必须在 09:00 硬截止点前完成。到点未成功则停止本期后续生成和发布；次日只生成新一期，不补发昨日内容，不无限重试或追补历史日期。
- 发布采用完整替换，失败不破坏已有日报；同一天最多一个日报地址，重试不得产生重复期刊。过期任务不得补发或覆盖较新一期的首页与收录历史。
- 已发布日报发现事实错误时，允许维护者沿用原地址更正，标明更正时间和更正说明，保留原发布时间。纠错不算新一期、不重置去重窗口、不顺带更换选题，也不新增审核后台或用户操作入口。

## 6. 数据与生成边界

采用“定时采集 → AI 相关性判断 → 顺序筛选与去重 → Agent 分析 → 校验 → 静态页面发布”的流程。维护最近收录历史以执行重复规则；历史日报持续归档，首版不自动清理。

以结构化 JSON 作为生成、校验和渲染的统一数据源，网页作为读者的阅读产物；首版不另做 Markdown 下载或对外 API。

一期数据至少包含：日报日期、时区、采集与发布时间、来源地址、统计口径、运行状态及条目列表。每个条目至少包含：仓库标识与链接、原始榜单位置、AI 相关性依据、项目类型、中文介绍、用途与适用读者、特点、热度指标、原因是否有明确依据、原因说明或未知说明、来源链接，以及适用时的重复收录依据与上期链接。

内部保存候选筛选结果、生成失败原因、调用消耗和收录历史，以便排查漏选、重复和预算问题。运行内部信息不塞进日报正文。模型返回内容须通过必填字段、链接来源及数值一致性校验；不能把模型生成的指标替代采集值。无法完成可靠分析的候选可跳过并继续按榜单顺序处理后续项目，留下内部原因；部分分析成功时，按规则处理完成后可发布成功条目。存在合格候选却全部分析失败、采集失败或处理流程整体未完成，均不得发布成“没有热点”，须按生成失败处理。上述处理和发布仍受 09:00 硬截止点约束。

保留固定榜单快照及其采集时间；收录历史区分期次所属日期的 09:00 计时时间与实际发布时间。发生纠错时保留更正时间、说明及原发布时间，不将更正写成新的收录事件。

## 7. 成本约束

每个自然月模型、托管及其他日常服务费用合计不超过人民币 30 元，不含开发成本。优先免费静态托管与定时调度，以及适合中文摘要的低成本模型。

- 对每次运行限制输入长度、输出长度、调用次数和重试次数；缓存同一轮已获取的数据和成功结果，避免重复计费。
- 接入付费服务前确认价格，结合服务限额及保守的调用成本预留控制预算；汇率费用也计入预算。记录实际或保守估算消耗。
- 预计下一次付费调用会超出剩余额度时停止调用，不自动升级或超额购买。不能完整生成时按生成失败及硬截止规则处理，并提示当月生成额度已用尽。
- 预算耗尽后，已有网页仍应可访问；下月额度恢复后继续调度。不承诺预算耗尽期间仍能每日更新。

模型、调度平台、托管平台的具体选择属于实现设计；必须先验证它们在预算内能支撑完整流程，不能仅以“免费额度”假定长期可用。

## 8. 首版不做

- 用户注册、登录、个人关注设置和个性化日报。
- GitHub 之外的信息源、榜外发现，以及整个 AI 行业的新闻覆盖。
- 邮件或消息推送、实时更新、用户手动触发生成。
- 主观推荐排名、深度源码或架构分析、项目实际运行与性能测试。
- 知识库搜索、问答、聊天、收藏及复杂知识关联。
- 人工审核后台、多语言切换及商业化功能。

维护者对已发布事实错误的更正不属于用户手动触发生成或每日人工审核，按第 5 节执行。

“AI 知识库”是最初构想，首版交付范围以本规格中的公共日报及历史归档为准。

## 9. 验收与验证

### 功能与边界验收

1. 从一次完整 Daily 榜单快照验证：仅纳入 AI 项目，包含符合条件的教程和合集；顺序与源榜单一致，最多 5 个，不从其他来源补足。
2. 验证首次收录、7 天内无变化、新正式 Release、Star 倍增、指标缺失、零基数、恰好满 168 小时和超过窗口等情况；确认按所属日期北京时间 09:00 计时，仅成功发布记录参与去重，失败、重试和纠错不重置窗口。
3. 抽查每个条目的来源：指标与采集结果一致，描述可追溯，无依据的原因明确为未知；缺失指标不会被编造成零。
4. 验证真正零项目、部分候选分析失败、合格候选全部分析失败、整体抓取失败、任务未启动、发布失败、截止前重试成功、截止时未完成和预算耗尽；失败不可伪装成空日报。确认到点放弃、次日仅生成新一期、过期任务不能补发或覆盖新一期，已有日报仍可访问，不冒充当日内容、不重复发布。
5. 手机与桌面均可打开最新一期及历史页面，无需登录；日期、实际发布时间和失败状态清晰。任务未运行时首页也能独立判断到点缺刊，首次无日报和历史页面状态正确。
6. 按实际服务定价验证调用上限、重试上限和月度预算控制，记录试运行消耗，不允许以无限重试换取成功率。
7. 验证同一期重试固定使用第一份有效完整快照，候选、原始顺序、指标和采集时间不混用，成功分析可复用；尚无有效快照时可重新抓取。
8. 验证维护纠错沿用原地址、保留原发布时间、显示更正时间和说明，不换选题、不新建期次、不重置收录窗口。

### 连续试读验收

由发起人连续试读 7 期，记录每期阅读耗时、至少一个有价值的项目及理由、事实问题和发布时间。

- 至少 5 期同时满足：10 分钟内读完，并且至少有 1 个项目让读者认为“知道它为什么受到关注，对我有价值”。未知原因不强行解释，但这一期仍须提供足以产生价值的热点信息。
- 7 期均不得出现编造热度数据或把推测当事实的情况；发现此类问题即不通过，需要修正生成约束后重新验证。
- 正常运行日须北京时间 09:00 可读；到点失败或缺刊如实记录，不以次日补发冒充当日成功，并验证失败展示、到点放弃及次日新一期调度流程。
- 记录 7 期运行费用及按实际调用量推算的月费用，确认预算可行；不能以 7 期成本未超 30 元替代月度预算验收。

达到上述标准后再考虑新增来源、个人设置或其他扩展；未达到时优先修正选题、事实准确性和阅读体验。
